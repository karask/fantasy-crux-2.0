# Rules style guide

How Fantasy Crux rules are written and illustrated. It applies to the website
rules in `src/content/rules/` and, later, to the print handbook.

The goal is rules that a player can read once, at the table, in their second
language, and apply correctly.

## Words and sentences

- **One rule per sentence.** Aim for 20 words or fewer. Split a sentence that
  needs a semicolon, a dash, or brackets to hold a second idea.
- **Talk to the player.** Use "you" for the character taking the action. Name
  the roles when two sides act: attacker and defender, Shaper and target.
- **Use plain verbs and active voice.** "Roll Dodge", not "Dodge is opposed".
- **Use "can", "must", and "cannot".** Avoid "may": it can mean permission or
  possibility. Avoid "thereafter", "such", "respectively", "whichever", and
  "otherwise" chains.
- **Say the general rule first, then the exceptions.** Put exceptions in their
  own short list, labelled **Exceptions** when there is more than one. Never
  hide an exception in the middle of a paragraph.
- **Keep British spelling.** Armour, defence, metres.
- **Write numbers as numerals** in rules: 3 metres, 1 PP, Intensity 2.

## Structure

- Open each rule with one or two sentences that say what it is for.
- Use numbered steps for a procedure, bullets for parallel options, and a table
  to compare three or more things on the same points.
- Use a **Yes/No table** to answer "can X do Y?" questions. Start each cell
  with Yes, No, or a value, then add the condition.
- Give each rule one home. Elsewhere, link to it rather than repeat it. A
  quick-reference table may restate rules only if it links to their home.
- Use an example only where a rule is easy to misread. Keep it to a few lines in
  a `> **Example.**` block.

## Game terms

- Capitalise game terms: Combat Action, Movement Action, Reaction, Dodge,
  Parry, Active Guard, Magnitude, Intensity, Reach.
- Define a term once, in bold, where it is introduced. Link to that place when
  the term is used far from it.
- Use one name per idea. Do not use these loose synonyms:

| Write                        | Not                               |
| ---------------------------- | --------------------------------- |
| Active Guard                 | shield guard, missile Parry       |
| Reaction                     | response, defence action          |
| Magnitude (`M`)              | level, cost (cost is the PP paid) |
| known cell                   | spell, cell you have              |
| Projected Harm / Direct Harm | projected attack, direct damage   |
| opposed test                 | contest, resisted roll            |
| `+1B` (Bonus die)            | +1 Bonus, advantage               |
| `-1P` (Penalty die)          | −1 Penalty, disadvantage          |
| Armour Points (AP)           | armour value, protection points   |

## Notation

- Dice and modifiers are code: `1D6`, `2D6 + DM`, `+1B`, `-1P`.
- Write a Shaping cell as `Technique·Form`, in code: `Unmake·Fire`.
- In tables, abbreviate Intensity, Range, Duration, and Magnitude as I, R, D,
  and M, as the examples table already does.

## Diagrams

Use a diagram when it shows something prose cannot show quickly: an order of
steps, a choice between paths, a scale, or a budget. Do not draw a diagram that
only repeats a table.

- **The text is the rule.** A diagram summarises. Every fact in a diagram must
  also be in the prose or a table beside it, so search, screen readers, and
  copy-paste still work.
- **Alt text states the rule** in one or two sentences, not the picture.
- **Few words.** Labels are short. Long explanations belong in the prose.
- **Readable on a phone.** Lay diagrams out for a narrow column first. Text
  must stay at least 10 pixels high at 320 pixels wide.

Diagrams are SVG files generated by `scripts/build-diagrams.mjs` into
`src/assets/diagrams/`. Rules Markdown embeds one with standard image syntax on
its own line, using a path relative to the Markdown file:

```md
![Damage passes Parry, then armour, then any vitality reserve; only the rest reaches HP.](../../../assets/diagrams/damage-steps.svg)
```

The build inlines the SVG so it uses the site fonts. Edit the generator, run
`npm run diagrams:build`, and commit both. `npm run diagrams:check` fails if a
committed SVG is out of date.

### Visual language

| Element       | Meaning                         | Style                                  |
| ------------- | ------------------------------- | -------------------------------------- |
| Step box      | Something you do                | Light paper fill, ink outline          |
| Header bar    | Name of a step or group         | Iron fill, bone condensed capitals     |
| Decision      | A question that splits the flow | Brass outline, brass tint              |
| Good outcome  | Hit avoided, no cost, allowed   | Steel-blue outline on a pale blue tint |
| Caution       | Allowed with a penalty, risky   | Brass outline on a pale brass tint     |
| Bad outcome   | Damage, Backlash, not allowed   | Oxide outline on a pale oxide tint     |
| Modifier chip | `+1B`, `-1P`, `+1 M`            | Monospace text in a small rounded chip |
| Arrow         | Then                            | Ink line with a solid head             |

Colour never carries meaning alone: pair it with a word, a mark, or a shape.

## Tables with verdicts

Add `{.verdicts}` on its own line, after a blank line below a table, to colour
its answer cells. Cells that start with **Yes** or **All** are tinted blue,
**Half** or **Yes** with a Penalty die brass, and **No** or **None** oxide. The
words still carry the meaning in plain Markdown.
